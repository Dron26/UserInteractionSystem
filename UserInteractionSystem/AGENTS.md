# AGENTS.md

## 1. Назначение проекта

Проект разрабатывается в рамках выпускной квалификационной работы.

Тема ВКР:

**«Автоматизация взаимодействия с пользователями (на примере ИП Четников Александр Александрович)»**

Тип системы: веб-информационная система.

Цель проекта — разработать небольшую информационную систему для учета клиентов, обращений и взаимодействий с пользователями.

Проект должен оставаться достаточно простым для понимания, реализации и защиты в рамках ВКР.

Главный принцип:

**Не сделать максимально много. Сделать достаточно, но качественно.**

---

## 2. Роль GitHub Copilot Agent

GitHub Copilot Agent является вспомогательным инструментом разработки.

Agent НЕ является самостоятельным архитектором проекта и НЕ должен самостоятельно определять бизнес-логику системы.

Студент принимает решения по:

* архитектуре;
* структуре данных;
* сущностям;
* бизнес-правилам;
* границам MVP;
* используемым технологиям;
* существенным изменениям существующей логики.

Agent помогает реализовывать уже принятые решения.

Главная цель использования Agent — ускорить разработку и помочь с рутинным кодированием, при этом студент должен понимать реализованный код и иметь возможность объяснить его на защите ВКР.

---

## 3. Обязательное правило понимания кода

Не создавать код, который студент не сможет понять и объяснить.

Если изменение является существенным, Agent должен объяснить:

1. какие файлы изменены;
2. что именно изменено;
3. зачем это изменение необходимо;
4. как изменение работает;
5. какие архитектурные или технические последствия оно имеет;
6. какие есть потенциальные проблемы или альтернативы.

Если для выполнения задачи требуется архитектурное решение, сначала предложить варианты и дождаться решения пользователя.

---

## 4. Правила принятия архитектурных решений

Agent НЕ должен самостоятельно:

* добавлять новые сущности;
* изменять существующую модель данных;
* вводить новые архитектурные слои;
* добавлять отдельные проекты в Solution;
* добавлять сторонние библиотеки;
* менять технологический стек;
* вводить новые API;
* создавать микросервисную архитектуру;
* добавлять сложные паттерны без необходимости;
* расширять MVP без согласования.

Если такое изменение кажется необходимым, Agent должен остановиться и сообщить:

* почему возникла необходимость;
* какие есть варианты;
* какой вариант предлагается;
* какие последствия имеет каждый вариант.

Окончательное решение принимает пользователь.

## 6. Архитектура

Проект представляет собой одно ASP.NET Core приложение с логическим разделением ответственности.

Предполагаемая структура:

```text
Domain/
    Entities/
    Enums/

Application/
    Interfaces/
    Services/

Infrastructure/
    Data/
    Configurations/

Web/
    Components/
    Pages/
    Layout/
```

Фактическая структура может уточняться по мере разработки, но усложнять архитектуру без необходимости запрещено.

Основной поток:

```text
Blazor UI
    ↓
Application Services
    ↓
Entity Framework Core
    ↓
SQLite
```

UI не должен напрямую содержать сложную бизнес-логику и самостоятельно работать с базой данных без необходимости.

## 7. Основные сущности MVP

В MVP используются следующие сущности:

### Client

Клиент системы.

Основные свойства:

* Id : int
* FullName : string
* Phone : string?
* Email : string?
* Comment : string?
* IsArchived : bool
* CreatedAt : DateTime

Удаление клиента физически не выполняется.

Используется архивирование.

---

### User

Пользователь системы.

Основные свойства:

* Id : int
* UserName : string
* PasswordHash : string
* FullName : string
* Role : UserRole
* IsActive : bool
* CreatedAt : DateTime

Основные роли:

* Admin
* Employee

---

### Request

Обращение клиента.

Основные свойства:

* Id : int
* ClientId : int
* ResponsibleUserId : int?
* Title : string
* Description : string
* Status : RequestStatus
* Priority : RequestPriority
* CreatedAt : DateTime
* UpdatedAt : DateTime
* CompletedAt : DateTime?

---

### Interaction

История взаимодействия по обращению.

Основные свойства:

* Id : int
* RequestId : int
* UserId : int
* Channel : InteractionChannel
* Content : string
* CreatedAt : DateTime

Interaction связан с Client через:

```text
Interaction
    ↓
Request
    ↓
Client
```

Не добавлять ClientId в Interaction без отдельного архитектурного решения.

---

## 8. Архивирование клиентов

Клиент не удаляется физически.

Используется:

```text
Client.IsArchived
```

Правила:

* обычный список показывает только неархивных клиентов;
* архивные клиенты сохраняются в базе;
* историю обращений и взаимодействий нельзя терять;
* архивный клиент может быть просмотрен;
* архивный клиент не редактируется;
* для архивного клиента нельзя создавать новое обращение;
* архивирование выполняет Admin;
* отдельная таблица архива не создается.

Не реализовывать физическое удаление клиента без отдельного решения пользователя.

---

## 9. Границы MVP

MVP должен включать только необходимую функциональность:

* авторизация;
* работа с клиентами;
* архивирование клиентов;
* работа с обращениями;
* обработка обращений;
* фиксация взаимодействий;
* история;
* завершение обращений;
* базовая панель Dashboard;
* управление пользователями для Admin.

Не добавлять без согласования:

* Company;
* мультиорганизационность;
* SaaS;
* внешние Telegram API;
* внешние WhatsApp API;
* email API;
* уведомления;
* загрузку файлов;
* сложную аналитику;
* микросервисы;
* отдельный REST API без необходимости;
* сложную систему аудита;
* сложные права доступа;
* дополнительные сущности только ради «масштабируемости».

## 10. Работа с задачами

Agent должен работать небольшими задачами.

Не выполнять запросы вида:

> «Полностью реализуй всю систему».

Предпочтительный процесс:

```text
Задача
↓
Анализ
↓
Предложение решения
↓
Реализация небольшого изменения
↓
Объяснение изменений
↓
Проверка пользователем
↓
Тестирование
↓
Git commit
```

Одна задача должна иметь понятный результат.

---

## 11. Работа с существующим кодом

Перед изменением существующего кода Agent должен:

1. определить связанные файлы;
2. понять существующую структуру;
3. не переписывать рабочий код без необходимости;
4. минимизировать область изменения.

Не выполнять массовый рефакторинг без отдельной задачи.

---

## 12. Работа с ошибками

При обнаружении ошибки:

1. определить причину;
2. объяснить причину;
3. предложить минимальное исправление;
4. внести изменение;
5. проверить результат.

Не исправлять ошибку путем отключения проверок, удаления функциональности или добавления временных обходных решений без объяснения.

---

## 13. Зависимости

Перед добавлением NuGet-пакета или другой зависимости Agent должен объяснить:

* зачем она нужна;
* почему стандартных средств .NET недостаточно;
* какие альтернативы существуют.

Не добавлять зависимости только ради удобства.

---

## 14. База данных

Используется Entity Framework Core.

Основная БД MVP:

**SQLite**

Первичные ключи основных сущностей:

```text
int
```

Не заменять их на Guid без отдельного решения.

Структура базы должна соответствовать утвержденной модели предметной области.

---

## 15. Безопасность

Пароли нельзя хранить в открытом виде.

Для хеширования паролей использовать стандартный механизм ASP.NET Core:

```text
PasswordHasher<TUser>
```

Не реализовывать собственный алгоритм хеширования.

---

## 16. Git

Изменения должны быть небольшими и логически связанными.

Не смешивать в одном изменении:

* новую функциональность;
* большой рефакторинг;
* изменение архитектуры;
* исправление несвязанных ошибок.

Перед commit пользователь должен понимать, что именно было изменено.

## 17. Документация проекта

Проект сопровождается документами ВКР.

Основные документы:

* `00_Главный_документ_проекта.md`
* `01_Требования.md`
* `02_Варианты_использования.md`
* `03_Проектирование_системы.md`

Документация определяет согласованные требования и архитектурные решения.

Если код противоречит документам, Agent не должен самостоятельно выбирать сторону.

Необходимо сообщить о противоречии и запросить решение пользователя.

---

## 18. Запрет на расширение проекта

Не добавлять функциональность только потому, что она «может пригодиться в будущем».

Будущие возможности могут быть описаны в документации, но не должны автоматически попадать в MVP.

Приоритет:

**простота → понятность → корректность → завершенность → расширяемость**

---

## 19. Требования к ответу Agent

После выполнения задачи Agent должен кратко предоставить:

### Изменено

Список измененных файлов.

### Что сделано

Краткое описание реализации.

### Почему

Объяснение технического решения.

### Проверка

Что было проверено и каким способом.

### Что осталось

Если есть нерешенные вопросы или следующие шаги — указать их.
